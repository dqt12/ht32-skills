# HT32 同系列型号迁移（migrate 工作流）

> 本文件是 `ht32` 主 Skill 的内部工作流（无 frontmatter，不是独立宿主 Skill），由主入口 `SKILL.md` 按意图路由进入。

把已有工程从一颗 HT32 型号换到**同一系列**的另一颗（如 HT32F50230 → HT32F50241）。
判定与差异全部走 MCP 取证；**跨系列（固件库不同）不支持迁移**——库不同意味着寄存器布局、
库 API 与启动文件都可能变，只能按 project-create 新建目标型号工程后人工搬运功能。

## 前置

1. 执行内部工作流 **env-check**（读取主包 `workflows/env-check.md` 按其流程执行）
2. 定位工程根目录：`--project` 指定 > 当前 workspace > 询问用户
3. 读取 `<工程根>/HT32_PROJECT.md`（上下文锚点；同目录 `AGENTS.md` 仅作薄引导，不承载事实）；
   不存在 → 先执行内部工作流 **project-context**（init）；型号等必要信息无法确定时**阻断**

## 执行流程

### 第 1 步 · 确定源型号与目标型号

- **源型号**：从 `HT32_PROJECT.md` 第 2 节「目标芯片」读取（实测值）；与实际 `.uvprojx` 的器件
  不一致时先与用户确认以哪个为准，不猜测
- **目标型号**：用户指定；未指定时用 wiki MCP `list_chips` + `get_chip_info` 列出同系列候选供选择，
  **不代替用户拍板**

### 第 2 步 · 迁移边界判定（同系列 = 同一固件库包）

判定依据**必须实测**，既不按型号命名想当然，也不维护写死的型号对照表
（工具参数与返回要点见本包 `references/mcp-tools.md`）：

1. code MCP `list_libraries`：取各固件库包覆盖的系列（如 `HT32_STD_5xxxx_FWLib` 覆盖 F5 系列）
2. wiki MCP `get_model` + `get_chip_info`：确认两个型号各自归属的系列页
3. 两个型号落在**同一固件库包** → 同系列，可迁移，继续第 3 步
4. 分属不同固件库包 / 不同内核家族 → **阻断**：说明「库不同，不能迁移」，给出替代路径
   （按 project-create 新建目标型号工程 → 用 dev-assist 搬运功能 → 人工比对），
   不擅自尝试跨库改工程

### 第 3 步 · 差异清单（wiki MCP）

用 `compare_chips([源型号, 目标型号])` + `get_chip_info` 逐项核对，产出差异清单：

| 核对项 | 影响判定 |
|---|---|
| Flash / SRAM | 变小 → 可能装不下，**阻断并说明**；变大 → 仅内存布局变化 |
| 内核 / 主频 | 变化 → 改系统时钟配置（CKCU / PLL），依据走 wiki 规格 + code 例程 |
| 封装 / 引脚数 | 变化 → **需改硬件与引脚分配**，逐引脚核对 |
| 工作电压 | 变化 → 提示硬件供电条件 |
| 外设与通道数 | 外设缺失 → 阻断该功能；通道/实例变化 → 改初始化与引脚配置 |

- 引脚与复用功能变化：走 wiki 引脚复用（pinmux）检索（`search_datasheets("<型号> pinmux")`；
  未命中再 `search_knowledge("<型号> <引脚号>", include_datasheets=True)`）
- 差异清单（含必需改动项与硬件影响）**先给用户确认**，**确认后才动工程文件**
- MCP 答不出 → 记知识缺口：对应 MCP `submit_feedback` 上报，清单中标「待核对（MCP 未覆盖）」

### 第 4 步 · 更新 HT32_PROJECT.md

执行内部工作流 **project-context**（update）：

- 第 2 节：目标芯片结论替换为新型号（**新值 + 新 wiki 来源成对更新**）
- 第 3 节：外设清单按差异调整（新增 / 移除 / 通道变化），资源占用说明同步
- 第 5 节：需求记录追加「型号迁移：<源型号> → <目标型号>」
- 第 6 节：变更记录追加迁移依据（wiki 页面 / code 例程路径）

### 第 5 步 · 工程改动（用户确认差异清单后）

- 改动点**逐项必须有依据**（wiki 规格 + code 例程 / 库知识），不凭记忆列点；典型改动面：
  - Keil 工程：器件选择与内存布局（IROM/IRAM）、`<SFDFile>` 指向新型号 SVD
  - 器件相关头文件宏与启动文件（按 code MCP 的模板 / 例程知识确认）
  - 库与 pack 版本：目标型号所在固件库包与 DFP 是否匹配（`list_libraries` + 环境检测结果）
- 时钟、引脚、外设实例等代码改动按第 3 步差异清单逐项落地
- 对照源/目标工程实际编译配置核对器件选择、汇编与 C 各自生效的预定义宏、条件编译分支和启动文件，确认两侧器件定义一致；宏名、取值及适用范围须由 code MCP 核实，不因型号迁移而盲目替换或沿用。
- 核验 Flash 算法/器件配置与目标型号匹配；Flash 等待周期/等待状态及其主频、供电条件依据查 wiki MCP，实现与工程配置查 code MCP。不复制源型号值，不给出未取证的通用数值。缺证据标记待核对并上报。
- 编译成功后仍需记录目标工程的器件/宏摘要、Flash 配置依据及编译日志；编译通过不等同于板级时钟或 Flash 时序已实测。
- 不修改 raw/ 冻结内容；不修改库文件本体（用户明确要求时除外，且记入 HT32_PROJECT.md 变更记录）
- 覆盖用户已有文件前先确认，不自动覆盖

### 第 6 步 · 编译回查

- `_ht32-runtime/ht32.py workflow run --project <工程路径> --steps build`，读取统一 JSON 的
  status、产物与日志路径；目标 **0 Error 0 Warning**
- 对照迁移核对表复查实际生效的预定义宏与 Flash 等待配置；无法由构建摘要确认的项目回读工程配置/构建日志，不以「编译通过」代替该核验。
- 失败 → 回到第 5 步按日志与依据修正；反复失败 → 停止，报告首错误 + 日志路径

### 第 7 步 · 收尾

- 在 HT32_PROJECT.md 变更记录追加迁移完成 + 编译结果
- 汇报：差异清单落地情况 + **每处改动的知识依据路径** + 遗留 TODO（含需改硬件的项）

## 失败处理

| 情况 | 处理 |
|---|---|
| 源 / 目标型号分属不同固件库包或内核家族 | **阻断**：库不同不能迁移，给替代路径（新建工程 + 功能搬运） |
| 目标型号 Flash / SRAM 装不下现有功能 | 阻断，附 wiki 规格依据 |
| 用户未确认差异清单 | 停在清单阶段，不动工程文件 |
| wiki 查不到目标型号 | 阻断，请用户确认型号拼写 |
| MCP 答不出器件宏 / 启动文件 / 库差异 | 记知识缺口 → 对应 MCP `submit_feedback` 上报 + HT32_PROJECT.md 标「待核对（MCP 未覆盖）」，不绕过 MCP 取证 |
| 编译错误循环 | 停止迭代，报告首错误与日志路径 |
| 发现本 Skill（流程/脚本/模板/环境检测）自身缺陷 | code MCP `submit_feedback(issue_type="skill_defect")` 上报（附 skill 版本号 + 现象 + 日志路径），不静默吞掉 |

## 核心规则

- **同系列判定 = 同一固件库包**（code MCP `list_libraries` 实测 + wiki 型号页核对），
  不按型号命名想当然、不写死型号对照表
- **跨系列不支持**：库不同即阻断，不尝试跨库硬改；替代路径是新建工程 + 功能搬运
- **先清单后改工程**：差异清单（含硬件影响）经用户确认后才动工程文件
- **取证只走 MCP**：规格 / 引脚依据来自 wiki-mcp，库 API / 例程 / 模板依据来自 code-mcp；
  **不得绕过 MCP 取证**，答不出即记缺口并上报
- HT32_PROJECT.md 是唯一事实源：迁移先更新它再动代码

## 全局 runtime 与项目数据边界
