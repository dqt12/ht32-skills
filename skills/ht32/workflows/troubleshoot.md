# troubleshoot（内部工作流 · 故障定位）

> 本文件是 ht32 skill 的内部工作流，由主入口按意图路由；不是独立 Skill，不带 frontmatter。
> 适用：程序不跑、跑飞、死机、复位环路、外设无输出、通信异常——"查不出原因"的问题。
> 不适用：编译 / 烧录工具报错（走 `keil` / `flash` 的失败排障路由）、串口采集本身的异常（走 `uart-print`）。

## 第 0 步 · 先把现象钉死

| 必须问清 | 为什么 |
|---|---|
| 复现率（每次 / 偶发 / 上电几次一次） | 100% 是逻辑错误；偶发优先怀疑时序、中断、供电 |
| 触发条件（上电、复位、烧录后、运行 N 秒、某个操作） | 指向启动流程 / 看门狗 / 状态机 |
| 现象（不跑、跑飞、卡死、重启、输出错） | 决定走第 1 步哪条分支 |
| 最近一次改动（代码 / 时钟 / 引脚 / 硬件） | 先怀疑改动，而不是怀疑整个工程 |
| 旧固件是否正常（有 `firmware/` 归档件就直接烧回去对比） | 一步排除硬件与工具链 |

现象没钉死就动手，等于在猜。信息不足时先问用户，不要自行假设。

## 第 1 步 · 按启动阶段三分支

| 阶段 | 判据 | 先查 |
|---|---|---|
| 根本没进 `main` | 在已烧录的当前固件入口设置断点，结合复位后的启动执行路径确认尚未进入；无打印或暂停时 PC 不在 `main` 仅作线索 | 时钟与启动文件、向量表、栈大小、BOOT 电平、复位源 |
| 进了 `main` 但死在半路 | 启动打印有，后续打印断在某一句 | 断点定位到最后一句，查该句依赖的外设时钟与引脚 |
| 跑了但行为错 | 有打印、现象不对 | 查数据通路（采样 / 协议 / 并发），不是查启动 |

- 开发板正常、自制板启动异常时，对比两块板的实际晶振/时钟输入与工程启动配置；先通过 code MCP 核实当前启动路径，再观察是否停在时钟就绪等待处，并通过 wiki MCP 核对目标型号的时钟条件。等待 HSE 只是候选原因，不直接认定为根因；确认不匹配后才转 dev-assist 修正，核验方法见 `references/clock-power.md`。

## 第 2 步 · HardFault / 复位环路

先判断当前是否有可用调试器；没有调试器时直接走本节 B，不得把读故障寄存器当成可执行前提。

### A. 有调试器

1. 暂停后读取 LR / PC / xPSR 与内核支持的 Fault 状态寄存器；CFSR / HFSR / MMFAR / BFAR 是否存在，按目标内核与芯片核实（Keil Fault Reports 窗口仅在该目标支持时使用）
2. 用 Call Stack 查看调用链；栈疑似损坏时记录 SP、栈区边界和附近内容
3. 归因候选按证据排查：空/野指针、越界、栈溢出、对齐限制、中断中不安全调用；不把候选列表当结论
4. 偶发 HardFault 同时检查并发访问、栈峰值、DMA 缓冲生命周期；按 code-style §8 选择同步方式，不以 `volatile` 单独作为修复
5. 从当前 Target 的链接设置和构建日志定位 `.map`、工具链支持的静态栈分析报告；先核实是否已生成及适用范围，不假定 runtime `artifacts` 包含这些报告。内存总占用不能代替栈用量结论。
6. 静态栈估计须注明间接调用、递归及中断嵌套等分析限制；结合当前 SP、链接定义的栈区边界和工程已有的运行峰值观测取证。仅在已确认初始化填充及观测机制有效时使用填充值检查；当前 SP 或静态报告均不能单独证明运行期最大栈用量。

### B. 没有调试器

1. **不写入用户代码或改写 HardFault 向量 / 启动文件来“抓现场”**；这会影响向量表与复位行为，除非用户明确要求且已核实芯片实现
2. 使用已有证据：看门狗/复位原因（寄存器和读取时机须先查目标型号资料）、已有串口最后一条日志、已有 GPIO 心跳/状态脚、故障前操作与复现时间
3. 若工程已有可用日志，在故障路径前后增加一条最小标记前须说明改动并经用户同意；没有串口时优先用现有 GPIO/LED，不凭空假设有空闲引脚
4. 没有任何可观测点时，报告当前证据不足；向用户询问是否允许增加观测点或接入调试器，不把推测写成根因

### C. 复位环路（两种环境都适用）

读复位原因区分看门狗 / 上电 / 软件复位 / 引脚复位；**具体寄存器、标志清除时机与 API 名先查 wiki
的复位控制器页并用 code MCP 取证**，不凭记忆写。若标志会被启动代码清除，必须在清除前观测。

结论必须落到"哪一行、哪个变量、什么值"或明确说明目前观测能力不足；不能把"可能是栈溢出"当结论。

## 第 3 步 · 外设级故障速查

| 现象 | 优先怀疑 |
|---|---|
| 外设完全不工作 | 时钟门控没开 / 引脚 AFIO 没配 / 复用编号错 |
| 偶发丢数据 | ISR 清标志时机、共享数据非原子、缓冲被覆盖 |
| 通信乱码 / 丢包 | 波特率与时钟源误差、引脚上下拉、共地 |
| 一开某外设就死机 | 中断优先级冲突、向量表未注册、栈不足 |
| 进低功耗唤不醒 | 唤醒源没使能 / 时钟被关 / 中断被屏蔽（见 `references/clock-power.md`） |
| 调试器连不上 | 先关 IDE 里的调试会话（与 UV4 命令行争用），再按 `flash` 的排障路由查 SWD 复用与供电 |

## 第 4 步 · 取证纪律

- **一次只改一处**，改完立即复测；不同时改时钟和代码
- 结论必须有寄存器值 / 打印 / 波形支撑；"应该是……"不算结论
- 先最小复现：把工程裁到只剩故障路径，再逐项加回
- 不猜寄存器名与库函数名：查 wiki 规格页 + code MCP `search_code_knowledge` / `find_example`
- 烧录失败后芯片里仍是**旧固件**，此时的现象不能当作本次改动的结果

## 收尾

- 工程有 `HT32_PROJECT.md` 时，根因、证据、修复方式写进第 6 节变更记录；没有时只在汇报中给出
- 根因若属风格问题（缺 `volatile`、ISR 里做长任务、共享数据非原子），
  按 `references/code-style.md` 第 8 节同时修正同类代码，避免同类问题复发

> 数据边界：项目 `.ht32-skills/` 只允许保存 `config.json`；state / cache / logs 写全局数据目录（不可写时降级，见 SKILL.md「数据目录与宿主沙箱」）。
